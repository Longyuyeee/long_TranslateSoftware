# Long翻译开发审计与后续路线

审计日期：2026-07-27

审计基线：`v0.4.8`；2026-07-30 滚动复审至 Native Messaging v1 协议阶段

最新的发布阻塞项、代码规模和逐阶段执行门槛见 [`DEVELOPMENT_STATUS_2026-07-30.md`](DEVELOPMENT_STATUS_2026-07-30.md)。

## 1. 结论

Long翻译已经完成从“功能原型”到“可持续发布的 Windows 产品”的第一阶段：

- 翻译、OCR、TTS、生词本、FSRS 复习、Anki、备份和 WebDAV 已形成完整闭环。
- 单实例、手动启动显示主界面、托盘、自动更新、DPAPI 敏感配置保护和签名更新链路已经落地。
- `v0.4.8` 已由 GitHub Actions 完成测试、Updater 签名、安装包、`latest.json` 和质量报告发布。
- 当前自动化基线为 36 个前端测试文件、154 项前端测试和 64 项 Rust 测试（含 2 项真实子进程测试）。

项目当前不缺少新的功能入口，主要矛盾已经变为：

1. 大型前端和 Rust 入口文件仍承担过多跨领域编排，修改成本和回归半径偏大。
2. 质量报告已经能衡量格式、路由和 OCR 基线，但真实双语语义、真实截图和真实发音样本仍不足。
3. 中英文词条数量一致，但国际化缺少自动化门禁，界面仍存在少量绕过词条表的硬编码文本。
4. 浏览器扩展尚未进入 UI 或 Host 代码阶段；桌面端与扩展之间的 Native Messaging v1 协议、安全边界和兼容契约已经先行落地。

因此，下一阶段应先完成 `v0.4.9` 架构与回归收口，再进入 `v0.5.0` 浏览器扩展。此时不建议并行增加文档翻译、实时语音或新的供应商插件体系。

## 3. 主要风险与优先级

### P0：发布信任与进程级回归

- Updater 包已经使用 Tauri 更新签名，但 Windows 安装包尚未配置 Authenticode，首次安装仍可能出现 SmartScreen 提示。
- CI 已启动真实应用子进程验证手动/自启参数契约，并覆盖单实例回调共用的恢复策略；GitHub Runner 缺少交互桌面，双实例聚焦与托盘图标唯一性仍需发布前人工烟雾。
- 自动更新已有 service/hook 测试和真实发布资产验证，但还应保留“旧稳定版安装后升级到当前版”的发版前检查。

### P1：大型文件和边界不清

- `Dashboard.tsx` 同时包含导航、七个页签、设置表单、同步、备份、诊断、生词本和历史视图。
- `api.ts` 同时承担供应商识别、请求组装、SSE、缓存、格式质量和 TTS 路由。
- `lib.rs` 已拆出多个领域模块，但仍集中注册命令、插件、窗口、快捷键和大量命令适配层。
- 前端与 Tauri 命令的错误契约仍需进一步统一，新增错误路径不应依赖自由文本匹配。

### P1：质量样本的代表性

- 当前翻译质量门槛主要证明格式不变量，没有衡量语义准确率、遗漏、幻觉和术语一致性的完整金标。
- OCR 的生成式 PNG 适合稳定回归，但不能替代真实应用截图、复杂背景、多显示器缩放和不同语言包的样本。
- TTS 目前验证路由和音频容器，尚未形成真实发音抽样、远端可用率和延迟趋势。

### P1：国际化与界面一致性

- 中英文词条当前完全对齐，但 `Record<Lang, any>` 无法在编译期阻止结构漂移。
- `Dashboard.tsx` 的品牌副标题仍固定为中文；`ErrorBoundary` 使用独立二分逻辑，没有复用统一词条表。
- 当前没有自动扫描新增界面文本或检测词条结构一致性的测试。

### P2：浏览器扩展的安全边界

- 扩展不能读取或保存桌面端 API Key、WebDAV 密码和数据库文件。
- 不能直接把 Tauri 命令暴露到任意网页；网页内容、扩展脚本与桌面进程之间必须有明确的信任分层。
- 必须先确定协议版本、授权、消息大小、超时、取消、错误码和断线恢复，再实现划词 UI。

## 4. v0.4.9：架构与回归收口

### 4.1 前端页面拆分

将 `Dashboard.tsx` 拆为导航壳和独立页签视图：

- `GeneralSettingsView`
- `BatchTranslationView`
- `ModelSettingsView`
- `AppearanceSettingsView`
- `WordbookView`
- `ReviewView`
- `HistoryView`

页签只接收明确的状态和操作接口；WebDAV、备份、诊断和配置持久化继续下沉到 hook/service。目标不是机械拆文件，而是让单个页签的修改不触碰其他页签的编排细节。

退出门槛：

- `Dashboard.tsx` 控制在 600 行以内。
- 新页签组件原则上控制在 400 行以内，超出时继续拆分领域区块。
- 页签切换、设置保存、批量翻译、生词本竞态和键盘导航测试保持通过。

### 4.2 前端服务拆分

将 `api.ts` 按职责拆分为：

- OpenAI 兼容请求与供应商能力描述
- SSE 流解析
- 翻译任务状态与主备切换
- 缓存上下文与格式质量
- TTS 路由

退出门槛：

- 网络传输、翻译策略、质量判断不再位于同一个文件。
- 超时、认证、限流、模型不存在、格式无效和取消使用稳定错误码。
- UI 不通过英文或中文错误文本判断恢复动作。

### 4.3 Rust 应用壳收口

继续把 `lib.rs` 中的命令适配层按领域移动到现有模块；应用入口只负责插件、窗口、托盘、快捷键、单实例和命令注册。

阶段进展（2026-07-30）：

- 配置命令已迁入独立模块，批量写入使用事务并保持 DPAPI 兼容迁移。
- 窗口、剪贴板与 OCR 遮罩命令已迁入 `system_integration.rs`，前端命令名和事件协议保持兼容。
- 多显示器虚拟桌面边界改为可测试的单一计算路径，覆盖负坐标；OCR 遮罩使用物理尺寸，修复高 DPI 环境下覆盖区域缩小的问题。
- Rust 自动化由 44 项增加至 47 项；`lib.rs` 降至 874 行并保留 16 个直接声明命令。
- 快捷键解析、启动注册、动态更新、暂停状态和模拟复制已迁入 `shortcuts.rs`；无效名称与组合被显式拒绝，注册或持久化失败时保留/恢复旧快捷键。
- 模拟复制改用原子忙碌状态与自动释放守卫，快速重复触发不会并发篡改剪贴板；捕获完成后重试恢复原文本剪贴板。

- 自启动切换以操作前后的 Windows 实测状态判断成功或拦截，不再依赖可能滞后的界面状态。

- Native Messaging v1 协议、威胁模型、兼容规则及 Rust/TypeScript 契约测试已完成；前端自动化增至 36 个文件 / 154 项，Rust 自动化增至 64 项（含 2 项子进程测试）。
- 下一阶段实现只负责 framing、来源校验和协议解析的最小 Native Host，再接桌面私有 IPC 与配对。

退出门槛：

- `lib.rs` 不再包含数据库查询、网络协议或文件格式实现。
- 所有前端可调用命令返回统一、可序列化的应用错误结构。
- 生产路径保持无用户输入可触发的 `unwrap` / `expect`。

### 4.4 国际化门禁

- 以中文词条结构推导英文词条类型，移除 `Record<Lang, any>`。
- 增加深层键一致性测试和占位符一致性测试。
- 把 ErrorBoundary 和品牌副标题纳入统一国际化策略。
- 在审查规则中禁止新增未豁免的用户可见硬编码文本。

退出门槛：

- 中英文键和插值占位符在 CI 中自动校验。
- 切换语言后无需重启即可更新所有主界面文本。

### 4.5 进程级和发布烟雾测试

- Windows 测试验证首次手动启动显示主界面。
- 再次启动只聚焦已有实例，不增加托盘图标。
- `--autostart` 仅进入托盘，手动启动不静默。
- 发版检查验证 `latest.json`、安装包 URL、签名字段和旧版升级路径。

阶段进展（2026-07-30）：

- 手动启动与 `--autostart` 已由真实可执行文件子进程在 Windows CI 中验证。
- 单实例再次启动、托盘菜单和左键点击统一调用受测的窗口恢复路径；关闭请求统一调用受测的隐藏路径。
- GitHub 托管 Runner 没有可靠交互桌面，无法稳定断言窗口前景权限和系统托盘图标数量；这两项保留为签名安装包发布前烟雾，不用脆弱自动化制造假安全感。

## 5. v0.5.0：浏览器扩展

### 5.1 技术方向

首版使用 Chrome / Edge 共用的 Manifest V3 代码，桌面端继续作为配置、密钥、翻译、术语表和生词本的唯一数据所有者。

桌面通信优先采用 Native Messaging，而不是向局域网开放 HTTP 服务：

- 安装器或桌面端注册受控 Native Messaging Host。
- 扩展只发送文本、页面来源、目标语言和用户动作。
- Host 返回翻译结果、结构化错误和收藏结果。
- API Key、WebDAV 密码、数据库路径和诊断内容永不返回扩展。

在实现前先建立版本化消息协议，至少包含：

- `protocolVersion`
- `requestId`
- `action`
- `payload`
- `capabilities`
- `success` / `error`
- `cancel`

同时限制消息大小、允许的扩展 ID、超时、并发数和可收藏字段。

阶段进展（2026-07-30）：

- `protocol/native-messaging-v1.schema.json` 已定义 `hello`、`pair`、`translate`、`add_word`、`cancel` 和 `ping`，并严格拒绝未知字段。
- Rust 与 TypeScript 使用同一组 v1 动作、响应类型和稳定错误码；测试覆盖版本不兼容、非法请求 ID、正文/术语表/消息上限、未知字段和来源精确匹配。
- Host 单条消息自限 1 MiB、翻译正文 32 KiB、术语表 100 项、会话并发 4 项；运行时按 UTF-8 字节数执行上限。
- 扩展来源必须与安装清单中的 `chrome-extension://<id>/` 完全匹配，不接受通配符；内容脚本不能直接获得桌面能力，必须经扩展 service worker 和显式配对。
- 当前交付是可审计协议契约，不代表 Native Host、Windows 注册、私有 IPC 或 Manifest V3 扩展已经可用。完整约束见 `NATIVE_MESSAGING_PROTOCOL.md`。

### 5.2 首版范围

只实现以下阅读闭环：

1. 网页划词后显示轻量翻译浮层。
2. 可选择带上有限前后文，默认不发送整页内容。
3. 复用桌面端目标语言、术语表和主备模型策略。
4. 一键收藏到桌面端生词本，并保存明确授权的来源页面信息。
5. 明确显示桌面端未运行、未授权、版本不兼容、翻译失败和收藏失败。

首版不包含：

- 整页双语替换
- PDF/字幕翻译
- 浏览器内保存 API Key
- 实时语音
- Firefox

### 5.3 分阶段交付

1. **协议原型（已完成）**：共享 schema、版本协商、双端模型和安全边界测试。
2. **桌面桥接**：Native Messaging Host、安装/注销、单实例兼容和结构化错误。
3. **扩展 MVP**：划词浮层、上下文开关、翻译和收藏。
4. **可靠性 Beta**：断线恢复、取消、超时、升级兼容、权限说明和隐私测试。
5. **稳定版**：Chrome/Edge 打包、桌面端版本检查、用户文档和独立发布门槛。

进入稳定版的门槛：

- 扩展侧不存在密钥和数据库访问能力。
- 协议兼容至少覆盖当前版与前一版桌面端。
- 网页脚本无法伪造未授权的 Native Messaging 请求。
- 翻译、收藏、取消、桌面端未运行和版本不兼容均有自动化测试。

## 6. 推荐执行顺序

1. 合并 Native Messaging v1 协议基线，但不把它视为可运行扩展。
2. 完成 `Dashboard.tsx`、`api.ts`、`lib.rs` 和 Tauri 错误结构的 `v0.4.9` 剩余收口。
3. 构建 `v0.4.9` 候选安装包，执行并留档交互桌面及 `v0.4.8` 升级烟雾。
4. 发布并核验 `v0.4.9` 全部资产。
5. 在 `v0.5.0` 实现最小 Native Host，再推进私有 IPC、配对和 Manifest V3 service worker。
6. 桌面桥接通过安全审计后再实现划词 UI。
7. 持续补真实翻译、OCR、TTS 样本与 WebDAV 服务兼容矩阵。
8. 评估 Authenticode 证书成本；获得证书后接入现有 Release 工作流。

这套顺序可以让 v0.5.0 复用稳定边界，而不是把桌面端现有复杂度复制进扩展。
