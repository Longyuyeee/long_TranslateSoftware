## 1. 结论

`v0.4.9` 已完成 Windows 桌面端的架构、启动/托盘、通知、界面适配和发布链路收口。下一阶段只保留两条产品主线：

1. `v0.5.0`：Chrome / Edge 浏览器扩展 MVP；
2. `v0.5.1`：PDF / Word 文档翻译 MVP。

两项能力不放进同一个发布版本。先把浏览器到桌面端的安全调用链做完整并发布，再建设文档解析、任务恢复和结构化导出。实时语音、新供应商插件、Firefox、整页网页替换以及其他办公格式继续延期。

## 4. 已确认缺口

### 4.1 浏览器扩展

仓库目前没有可运行的 Native Host、Windows Host 注册器、本机私有 IPC、桌面配对界面、Manifest V3 工程、service worker、content script 或划词浮层。现有交付仅是协议契约，不能被描述为“扩展已经可用”。

另一个架构约束是：当前翻译任务主要运行在 Tauri WebView 的 TypeScript 层。Host 接入时必须建立受测的桌面请求代理，不能让独立 Host 直接读取 API Key、数据库或复制一套翻译实现。

### 4.2 PDF / Word 文档翻译

仓库目前没有 PDF 文本层解析、DOCX Open XML 解析/重建、文档分段模型、长任务检查点或文档预览。现有批量翻译只处理一个文本输入，不适合直接循环调用来翻译整份文档，原因包括：

- 每个文本任务都会独立读取配置和术语表，无法形成稳定的文档级配置快照；
- 没有页、段落、表格单元格、样式和原文位置映射；
- 没有有界并发、断点续跑、逐段重试及安全的临时输出替换；
- 普通文本格式检查不能证明 DOCX 结构或 PDF 阅读顺序正确。

因此，文档翻译必须新增独立领域模块，但底层翻译请求、错误归一化、术语表和主备切换仍应复用。

## 5. v0.5.0：浏览器扩展 MVP

### 5.1 用户可见范围

- 支持 Chrome 与 Edge，共用 Manifest V3 代码；
- 用户在普通网页划词后打开轻量翻译浮层；
- 默认只发送选中文本，用户明确开启后才附带有限前后文；
- 复用桌面端目标语言、术语表、主模型和备用模型；
- 支持复制译文和一键收藏到桌面端生词本；
- 对桌面端未运行、未配对、版本不兼容、超时、取消、限流、翻译失败和收藏失败给出明确状态。

### 5.2 必需的底层范围

这些工作不作为独立产品功能扩张，但属于扩展 MVP 的必要组成：

1. **Native Host 运行时**：二进制 stdin/stdout framing、解析 JSON 前的 1 MiB 限制、stderr 日志、精确 Origin 校验和 v1 协议解析。
2. **Windows 安装集成**：Chrome/Edge Host manifest、当前用户注册、升级和可逆卸载；安装失败不得留下半注册状态。
3. **桌面请求代理**：Host 通过仅限本机用户的私有 IPC 请求已运行桌面端；处理启动、超时、取消、并发上限、断线清理和请求关联。
4. **配对授权**：首次连接由桌面端显示真实扩展 Origin 和申请能力；支持拒绝、撤销和重新配对。
5. **扩展运行时**：service worker 独占 Native Messaging 权限，content script 只传递白名单动作，网页脚本不能直接调用 Host。

### 5.3 实施顺序

1. Host 仅实现 `hello` / `ping`，完成 framing、超限、非法 JSON、非法 Origin 和子进程测试；
2. 加入 Chrome/Edge 注册器，验证安装、重复安装、升级和卸载；
3. 建立私有 IPC 和桌面请求代理，先跑通 `hello` / `pair`；
4. 接入 `translate` / `cancel` / `add_word`，复用桌面翻译核心；
5. 实现扩展 service worker、content script 和隔离样式的划词浮层；
6. 完成真实浏览器烟雾、隐私审计、打包说明和发布候选。

### 5.4 发布门槛

- 扩展不保存或返回 API Key、WebDAV 密码、数据库路径及诊断内容；
- 未授权 Origin、未知字段、超限消息和不兼容版本默认拒绝；
- 网页脚本无法绕过 service worker 直接获得桌面能力；
- Host 或桌面端断开后没有孤儿翻译任务；
- Chrome 与 Edge 均通过安装、配对、翻译、取消、收藏、升级和卸载烟雾；
- 扩展 UI 支持中英文、亮色/暗色主题、键盘关闭和基本焦点管理；
- 正式发布前完成扩展包与桌面版本兼容矩阵。

## 6. v0.5.1：PDF / Word 文档翻译 MVP

### 6.1 文件与导出边界

- Word 首版只支持 `.docx`，不支持旧二进制 `.doc`；
- PDF 首版只支持具有可选择文本层且未加密的 `.pdf`；
- DOCX 输出为译文版或双语版 `.docx`，保留段落、标题、列表、表格和基础样式结构；
- PDF 首版提取阅读顺序并导出译文版或双语版 `.docx`，不承诺像素级还原原 PDF；
- 扫描版 PDF、复杂多栏重排、公式、手写内容、批注、修订和嵌入对象在导入检查时明确提示不支持或降级。

这个边界优先保证“内容完整、顺序可检查、任务可恢复”，避免用不可靠的版式复刻制造文件损坏或错译风险。

### 6.2 文档任务模型

新增独立文档领域，而不是在现有批量文本页堆叠条件分支：

```text
导入检查 → 解析结构 → 生成稳定分段 → 翻译队列
        → 逐段校验/重试 → 重建文档 → 原子导出
```

每个任务至少保存：文档指纹、格式、源/目标语言、配置快照摘要、分段 ID、原文位置、结构类型、状态、译文、错误和输出路径。任务默认有界并发，支持取消、失败段重试和应用重启后的断点继续。

文档二进制、图片和未选中的内容不发送到模型服务；只发送当前分段文本、必要的有限上下文和匹配术语。临时文件必须位于独立任务目录，成功后原子写入用户选择的输出位置，取消或失败时不得覆盖原文件。

### 6.3 实施顺序

1. 定义 `DocumentJob` / `DocumentSegment` 契约、状态机、检查点格式和隐私边界；
2. 抽出可供单次文本、浏览器和文档队列共享的翻译执行核心，配置与术语表按任务快照读取一次；
3. 先完成 DOCX 解析、稳定分段、基础结构重建和夹具测试；
4. 实现有界翻译队列、进度、取消、失败段重试和断点继续；
5. 完成 DOCX 译文版/双语版导出和结构验收；
6. 增加文本型 PDF 导入、阅读顺序预览与 DOCX 导出；
7. 完成真实文档烟雾、长文档稳定性、隐私审计和发布候选。

### 6.4 发布门槛

- 不覆盖源文件，取消、崩溃或磁盘写入失败不会产生伪装成成功结果的损坏文件；
- DOCX 夹具覆盖段落、标题、列表、表格、超链接、页眉页脚和中英混排；
- PDF 夹具覆盖单栏、多页、页眉页脚、断行和不可解析/加密文件的明确拒绝；
- 进度按稳定分段计算，失败段可单独重试，恢复后不会重复已完成请求；
- 文档翻译使用任务级配置与术语快照，处理中途修改设置不会污染同一任务；
- 输出经过重新打开与结构校验，用户可在导出前检查分段顺序和失败项；
- 建立小型、长文档和取消/恢复的固定质量与性能基线。

## 7. 明确延期

在 `v0.5.0` 和 `v0.5.1` 发布前，不并行开发：

- 整页网页双语替换；
- 扫描 PDF 全自动 OCR 翻译和像素级 PDF 版式重建；
- `.doc`、Excel、PowerPoint、EPUB、字幕等更多格式；
- Firefox、macOS 或 Linux；
- 实时语音同传；
- 新供应商插件体系；
- 浏览器侧密钥、独立模型配置或数据库同步。

## 8. 每一步的交付要求

- 一个 PR 只处理一个可审计边界，并同时加入对应测试和失败路径；
- 新增协议、任务状态和文件格式必须先固定契约/夹具，再接 UI；
- 继续运行前端测试、生产构建、包体审计、依赖审计、Rust 测试、严格 Clippy 和质量报告；
- 浏览器与文档功能分别维护真实 Windows 烟雾清单，不能只以单元测试代替最终交互验收；
- 不提交历史安装包、临时文档、用户文档内容、密钥或包含原文/译文的诊断数据；
- 每个阶段在 CI 通过后才合并，发布仍由版本标签触发 GitHub Actions。
