## 1. 文档用途

本文档是 `v0.5.1` 的唯一执行清单。后续开发必须按本文顺序推进，每一步分别完成实现、测试、审计、提交、推送和 CI 复核，不把多个高风险边界塞进同一个 PR。

历史审计和开发计划继续保留作为背景资料；当其状态或范围与本文冲突时，以本文为准。

## 2. 本版本范围

### 2.1 必须交付

- 只支持具有有效 Open XML 包结构的 `.docx`。
- 导入前检查格式、大小、压缩包安全边界和不支持内容。
- 生成稳定、可恢复的文档翻译任务和分段。
- 整个任务使用一次性冻结的服务商、模型、提示词和术语表快照。
- 支持有界并发、取消、失败段重试、应用重启后恢复。
- 支持译文版和双语版 DOCX 导出。
- 保留可支持的段落、标题、列表、表格、超链接、页眉、页脚和非文本资源。
- 源文件永不被覆盖；失败不得留下可被误认为成功的输出文件。
- 提供最小但完整的导入、风险提示、预览、进度、取消、恢复、重试和导出界面。
- 完成自动化门禁、真实 Windows 文档烟雾、升级验证、README 和 Release。

### 2.2 明确不进入 v0.5.1

- PDF 文本层解析、扫描 PDF OCR、PDF 版式重建。
- 旧二进制 `.doc`。
- 批注、修订、公式、嵌入对象、宏和复杂文本框的完整翻译；必须检测并明确警告或拒绝。
- 像素级版式还原。
- Chrome Web Store、Edge Add-ons 正式上架和正式扩展 ID 切换。
- Windows Authenticode、SmartScreen 信誉建设。
- 与文档链路无关的大型架构重构或新产品功能。

以上项目进入 `v0.5.2+`，不得为了“顺手完成”扩大本版本范围。

## 3. 固定开发、审计与推送流程

每一步必须遵守以下顺序：

1. 从已通过 CI 的最新 `master` 建立一个边界单一的 `codex/` 分支。
2. 开发前重读本步骤范围、退出门槛和上一阶段遗留风险。
3. 先补失败路径和边界测试，再完成实现；不得只验证成功路径。
4. 运行本步骤专项测试和第 12 节的通用质量门禁。
5. 审计本次差异：安全、隐私、资源上限、取消、崩溃恢复、兼容性和文档一致性。
6. 只提交本步骤相关文件，不夹带本地临时文件、密钥、用户数据或其他未关联修改。
7. 使用有明确范围的提交信息提交并推送，建立或更新对应 PR。
8. 等待 GitHub CI 完成；CI 失败必须在当前步骤修复，不带病进入下一步。
9. 将实际完成项、测试数量、残余风险和下一步入口写回本文或接手文档。
10. PR 合并后重新同步 `master`，确认工作区和远端基线，再进入下一阶段。

每个 PR 的说明必须包含：

- 本次解决的问题和明确不解决的问题；
- 用户可见变化；
- 数据、隐私和安全影响；
- 自动化测试与人工验收结果；
- 已知限制、回滚方式和后续步骤。

## 7. 阶段 3：有界翻译队列、取消与失败重试

### 实现任务

- [x] 复用任务级冻结的翻译执行快照，任务运行中修改设置不影响当前文档。
- [x] 默认并发为 3，硬上限为 8；队列和结果数组均受资源上限保护。
- [x] 每段完成后按节流策略保存 Checkpoint，避免每个流式 Token 写盘。
- [x] 支持任务取消、进行中请求中止、等待队列清空和应用退出清理。
- [x] 只重试失败段，使用有上限的退避；格式错误与永久错误不得无限重试。
- [x] 进入 `rebuilding` 前强制验证所有段已翻译，或执行用户明确选择的失败段回退规则。
- [x] 明确进度计算，恢复后不得倒退或超过 100%。

### 自动化验收

- [x] 并发上限、任务隔离、精确取消、超时、限流和乱序完成均有测试。
- [x] 任务运行中切换服务商、模型、Prompt 或术语表不会改变冻结快照。
- [x] 取消后不继续写入译文，不产生“完成”状态。
- [x] 重试只处理失败段，成功段不会重复计费或被覆盖。
- [x] 未全部完成时无法进入重建阶段。

### 2026-08-13 第一增量审计记录

- 新增纯调度层 `startDocumentTranslationQueue`，复用已有 `executeTranslationWithSnapshot`，不复制翻译协议、缓存、主备切换或格式校验逻辑，也不引入新依赖。
- 任务只接受 `ready` 状态和与 Checkpoint 完全一致的持久化快照；运行期 API Key 仅存在于同一个冻结执行快照中，不进入任务状态、进度回调或错误。
- 队列使用任务契约中的并发值（默认 3、校验硬上限 8），保持原始段数组顺序；乱序完成不会让完成数超过总数。
- 取消会先进入 `cancelling`，中止所有进行中请求，进行中段回到 `pending`，等待段不会启动，最终进入 `cancelled`；供应商自行抛出的 `AbortError` 不冒充用户取消。
- 单段失败不会丢弃其他成功译文；限流、超时、网络和服务端错误标记为可重试，错误按 UTF-8 截断到 Checkpoint 的 4 KiB 上限。自动退避和只重试失败段留给第二增量。
- 只有全部段为 `translated` 才能进入 `rebuilding`；否则任务进入结构化失败。Checkpoint 节流、恢复接线、应用退出清理和 UI 仍未包含。
- 本地验收：前端 51 个文件 / 250 项测试，桌面与扩展生产构建，主 chunk 235.96 KiB / 300 KiB，扩展 34.33 KiB / 64 KiB，npm 高危审计 0 漏洞。

### 2026-08-14 第二增量审计记录

- 新增 500 ms 尾沿节流的 Checkpoint writer；快速状态变化只保留最新的完整 v1 快照，所有真实写入通过 Promise 链串行化，不会并发替换同一任务文件。
- 队列每次状态更新只调度 Checkpoint，不保存流式 Token；任务进入 `rebuilding`、`cancelled` 或 `failed` 后绕过剩余节流窗口强制 flush，保证调用方收到完成结果前终态已经落盘。
- Checkpoint 保存失败不会被后台 Promise 吞掉：writer 停止后续保存、取消进行中的翻译请求，并让任务完成 Promise 以原始存储错误拒绝，避免 UI 误报成功或继续产生费用。
- writer 每次调度都先通过现有 v1 白名单校验并深拷贝，不持有会继续变化的任务引用；保存入口继续复用 Rust 同目录原子替换与恢复规则。
- 新增节流合并、运行中到期写入串行化、终态强制落盘和存储失败触发取消测试。失败段有界退避和恢复后的选择性重试仍属于下一增量。

### 2026-08-14 第三增量审计记录

- 单次队列运行中每段默认最多自动重试 2 次，硬上限 3 次；退避从 500 ms 指数增长并封顶 30 秒，避免网络抖动或限流形成请求风暴。
- 只有 `rate-limited`、`timeout`、`network` 和服务端错误自动重试；鉴权、模型、格式和未知错误立即保留为失败，不以重试掩盖配置或内容问题。
- 退避等待绑定任务 AbortSignal；用户取消或 Checkpoint 存储失败时立即中止等待，不会启动下一次可能计费的请求。
- `prepareDocumentJobForFailedSegmentRetry` 只接受 `failed` 任务，只把明确标记为可重试的失败段转回 `pending`；已翻译段的译文与尝试次数保持不变，永久失败段继续保留供用户处理。
- 崩溃恢复后的 `ready` 任务自然跳过 `translated` 段，只继续 `pending` 段；若之后显式重试失败段，同样不重发成功段。
- 新增指数退避、重试次数封顶、永久错误不重试、退避中取消和恢复后选择性重试测试。

### 2026-08-14 第四增量审计记录

- 新增 `DocumentTranslationTaskRegistry` 作为任务所有权边界；同一任务 ID 在未结束前不能重复启动，避免两个队列同时写同一 Checkpoint 或重复请求计费。
- 不同文档任务保持独立 AbortController 和完成 Promise；取消一个任务不会影响其他任务，任务完成、失败或取消后自动从注册表释放。
- 提供幂等的单任务取消和统一 `cancelAll`，供后续 UI 卸载、窗口关闭或应用退出路径调用；注册表不监听全局浏览器事件，生命周期所有权仍由接入它的 UI 明确控制。
- 注册表继续复用持久化队列，取消后的终态 Checkpoint 会在任务 Promise 完成前 flush；退出清理不会绕过既有存储错误传播规则。
- 新增重复启动拒绝、多任务隔离、单任务取消、统一退出取消和完成后可重新启动测试。结合既有冻结快照测试，阶段 3 的无 UI 自动化退出门槛已满足。

## 8. 阶段 4：DOCX 重建与安全导出

### 2026-08-14 第一增量审计记录

- 新增 `createDocxRebuildPlan` 白名单 preflight；只接受处于 `rebuilding` 的 DOCX 任务和绝对 `.docx` 输出路径，前端首先拒绝源路径覆盖。
- 重建前必须用重新读取源文件得到的 inspection 核对指纹、文件名和字节大小，源文件自导入后有任何变化都会停止，而不是把旧锚点应用到新内容。
- 每个替换项逐一核对稳定 ID、连续顺序、ZIP 部件、`paragraph/chunk/bytes/run/text-node` 锚点、结构类型和原文；缺少译文、锚点漂移或段数变化均拒绝。
- 计划只携带重建所需的源/目标路径、指纹、输出模式和替换白名单，不包含 API Key、运行期服务商凭据或其他设置。
- 当前增量只固定跨前后端重建契约，不写 ZIP、不改 XML、不创建输出文件；Rust 端仍必须独立复核所有限制并执行同卷临时文件与原子发布。

### 2026-08-14 第二增量审计记录

- 新增 Rust `validate_docx_rebuild_plan` 命令和 `deny_unknown_fields` 白名单模型；前端计划不能绕过后端校验，未知字段和任何额外 `apiKey` 会在命令执行前拒绝。
- Rust 从计划中的源路径重新打开 DOCX，并复用既有受限 ZIP/OPC inspection；重新计算的 SHA-256 与计划不一致时返回稳定的 `stale-source`，不会继续重建。
- 后端逐段重新核对 ID、连续顺序、ZIP 部件、结构、原文和完整 `paragraph/chunk/bytes/run/text-node` 锚点；不接受缺失文本节点范围的降级定位。
- 后端独立限制 20,000 个替换、单段译文 32 KiB、总译文 24 MiB，并再次拒绝相同源/目标路径和非绝对 `.docx` 输出。
- 校验成功只返回替换数、涉及部件数和译文字节数，不回传原文、译文、路径或凭据；当前仍不修改 XML、不创建临时文件或输出文件。
- 真正发布时仍须 canonical 化父目录并处理 Windows 路径别名、目录联接、目标已存在和文件占用；当前词法路径检查不替代发布边界。

### 2026-08-14 第三增量审计记录

- Rust 校验命令现在使用同一次受限读取完成重新 inspection、内存重建和重建后复检，避免校验与变换之间再次打开源文件产生竞态；全过程仍不创建目标文件。
- 译文模式按照原文本节点的 Unicode grapheme 权重分配译文，保留既有 Run、超链接、表格、列表、页眉和页脚容器；节点数量与结构不因译文长度变化而删除。
- 双语模式明确为“原段落保持不变，在同一段落末尾新增硬换行和译文 Run”；译文不进入原有超链接，新增 Run 使用段落默认字符样式。
- 非法 XML 1.0 控制字符在变换前拒绝，`&`、`<`、`>` 和复杂 Unicode 由 XML writer 转义；单 XML 部件、总包和译文资源上限继续独立执行。
- 修改过的 XML 部件使用原条目的压缩方法和元数据重写，未修改 ZIP 条目通过 raw copy 保留压缩数据、CRC 和内容；重建包会重新验证 OPC、关系、关键 XML 和可提取文本。
- 自动化覆盖多 Run 锚点分配、双语硬换行、XML 注入字符、非法控制字符、未修改媒体条目保留，以及命令完成后源文件不变且目标文件不存在。
