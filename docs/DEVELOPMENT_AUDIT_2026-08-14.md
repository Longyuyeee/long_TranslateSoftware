# 2026-08-14 开发进度与收尾审计

审计基线：`master` / `3053b8f`

目标版本：`v0.5.1` DOCX-only MVP

审计范围：PR #64～#74、DOCX 导入/持久化/队列/重建代码、前端接入、CI/Release 工作流、版本与用户文档一致性。

## 结论

项目已经完成 DOCX 文档翻译的无 UI 核心闭环：安全导入与稳定分段、Checkpoint 持久化、可恢复有界翻译队列、安全重试、任务所有权、重建计划复核、内存 XML/ZIP 重建和不覆盖原子发布均已进入 `master`。

当前还不是可发布的 `v0.5.1` 候选版。用户界面尚未把这些服务串成可操作流程，重建阶段没有任务级取消入口，真实输出兼容性与故障矩阵尚未完成，Release 工作流门禁仍低于普通 CI，所有版本源也仍是 `0.5.0`。

## 已完成并有自动化证据的范围

### 阶段 1：DOCX 安全导入与稳定分段

- PR #64 已合并；后端验证 ZIP/OPC 内容类型、Relationship、内部目标、重复与危险路径、压缩比、条目数、XML 和总展开体积上限。
- 正文、标题、列表、表格单元格、超链接及被引用的页眉页脚按稳定顺序提取；段锚点包含 paragraph、chunk、byte、Run 和 text-node 范围。
- 50 MiB 输入、32 KiB 单段、24 MiB 总文本、20,000 段及 48 MiB inspection 结果均有硬上限。

### 阶段 2：Checkpoint 与崩溃恢复

- PR #65～#66 已合并；Checkpoint 使用版本化白名单、任务私有目录、受限原子替换、损坏隔离和未来版本拒绝。
- 并发保存、替换失败、Windows 文件独占、过期终态清理和旧文件保全已有自动化覆盖。
- API Key、带凭据 URL、查询参数和片段不会进入 Checkpoint。

### 阶段 3：有界队列、恢复与失败重试

- PR #67～#70 已合并；队列具有并发上限、精确取消、失败隔离、串行节流 Checkpoint、终态强制落盘和任务注册表。
- 只自动重试限流、超时、网络和服务端错误；成功段保持不可变，恢复后不重复请求或重复计费。
- 同一任务不能重复启动，多任务取消相互隔离，应用退出可统一 `cancelAll`。

### 阶段 4：DOCX 重建与安全发布核心

- PR #71～#74 已合并；前端和 Rust 分别复核重建计划，Rust 重新读取同一源快照并检查 SHA-256、逐段锚点和资源上限。
- 译文按 Unicode grapheme 权重分配到既有文本节点；双语模式保留原段落并追加硬换行译文 Run。
- 未修改 ZIP 条目 raw copy；重建结果重新通过 OPC、Relationship、关键 XML 和可提取文本检查。
- 发布使用 canonical 目标父目录、同卷 `create_new` 临时文件、`sync_all`、落盘字节复核和不覆盖原子发布；源文件及既有目标不会被覆盖。
- PR #74 的最终 Windows CI run `31726094322` 全绿。该基线本地记录为前端 53 个测试文件 / 266 项测试，Rust 134 项单元测试通过、1 项人工语料测试显式跳过，另有 11 项集成测试通过；Clippy、构建、依赖审计、浏览器 Runtime Smoke 和质量报告均通过。

## 当前缺口与风险分级

### P0：用户闭环尚未接入

- 当前 DOCX 能力只存在于 service 和 Tauri command；`BatchTranslationView` / `Dashboard` 没有文件选择、inspection、分段预览、任务进度、恢复、重建或导出编排。
- 新用户无法从现有界面完成“选择 DOCX → 确认 → 翻译 → 恢复/重试 → 选择模式与目标 → 导出”。
- 在 UI 接通前，不能把文档翻译写入 README 的稳定功能表，也不能提升版本发布。

### P0：取消尚未贯穿重建与落盘

- 翻译队列已有 AbortSignal 与任务注册表，但同步 `rebuild_docx_document` 尚无任务 ID 或取消令牌。
- UI 关闭、应用退出或用户取消发生在重建期间时，当前只能等待同步命令结束；文档中的“取消不产生假成功”退出门槛尚未满足。

### P1：真实输出兼容性证据不足

- 导入阶段已有真实 DOCX 夹具与 LibreOffice 渲染审计，但重建后的译文版/双语版尚未完成至少 5 份匿名真实文档的 Word + LibreOffice 双重人工验收。
- 磁盘写满、临时文件/目标占用、权限拒绝、重建中取消及 50 MiB/最大段数边界还没有完整成品矩阵。
- 当前自动化证明包可重新解析，不等价于证明 Word 排版和可读性没有不可接受降级。

### P1：发布门禁与版本尚未收口

- 普通 CI 包含扩展包体积、浏览器 Runtime Smoke 和 Windows 生命周期测试；`release.yml` 尚未运行这三项同等级门禁，正式发布门低于合并门。
- `package.json`、`src-tauri/Cargo.toml`、`src-tauri/tauri.conf.json` 仍为 `0.5.0`，尚无 `docs/releases/v0.5.1.md`。
- 本次审计已纠正 README 停留在 PR #64 的过期开发状态；在 UI 接通并通过验收前，稳定功能表继续只标记为“v0.5.1 开发中”。

### P2：治理与长期质量

- v0.5.1 Milestone、分阶段 Issue、匿名可再分发 DOCX 语料、模糊测试种子和长文档性能/内存基线仍未建立。
- 浏览器商店正式 ID、完整 Chrome/Edge 安装生命周期和 Authenticode 不阻塞 DOCX MVP，但必须保留为独立风险，不得混入本次收尾。

## 后续开发顺序与验收目标

### 第一步：阶段 5A，建立最小 DOCX 工作台

- 使用系统文件选择器选择 `.docx`，展示文件名、大小、段数、支持警告和预计工作量。
- inspection 结果转换为任务后，提供分段预览、翻译确认、译文/双语模式与目标位置选择。
- 只接既有 service/command，不在组件内复制状态机、翻译协议、Checkpoint 或路径安全逻辑。

验收：组件/服务测试覆盖正常导入、拒绝文件、重复点击、输出冲突和稳定错误码；用户无需手输路径。

### 第二步：阶段 5B，接通任务生命周期与取消

- UI 通过 `DocumentTranslationTaskRegistry` 启动、取消、恢复和只重试失败段；进度来自持久化任务快照。
- 为重建阶段引入任务级取消边界，确保取消发生在内存重建、临时写入或发布前时不会生成最终输出，并清理临时文件。
- 窗口卸载与应用退出必须等待取消/Checkpoint 收口，禁止假成功。

验收：快速取消、窗口卸载、强制结束后恢复、多任务隔离和重建取消均有自动化与人工证据。

### 第三步：阶段 6，真实文档与故障矩阵

- 对至少 5 份匿名真实 DOCX 执行 import → translate fixture → rebuild → reopen，并分别用 Word 和 LibreOffice 检查译文版与双语版。
- 覆盖段落、表格、列表、链接、图片、页眉页脚、复杂 Unicode、空/超长译文、磁盘写满、权限不足、目标占用和资源上限。
- 记录峰值内存、长文档耗时、Checkpoint 大小和重建耗时基线。

验收：源文件哈希在全部成功/失败/取消路径保持不变；没有临时残留或可误认为成功的损坏输出。

### 第四步：阶段 7，发布收口

- 先让 Release workflow 补齐普通 CI 的浏览器 Runtime Smoke、Windows 生命周期和扩展包审计。
- 再统一版本为 `0.5.1`，更新 README、发布说明和下载链接，执行 NSIS/MSI 安装、v0.5.0 原位升级、Updater 与资产完整性验收。
- 只有 UI、取消、真实文档和发布候选矩阵全部通过后，才创建 `v0.5.1` 标签和 Release。

## 下一步入口

从阶段 5A 开始：先建立最小 DOCX 工作台和 UI 编排契约，不继续扩展后端格式或引入 PDF。该步骤完成并独立审计、推送、CI 全绿后，再进入阶段 5B 的任务生命周期与重建取消。
